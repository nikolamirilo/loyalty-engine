Loyalty Engine · design proposal

Automatic segments

A segment can be Manual, as it is today, or Automatic. An automatic segment is defined by conditions, in the same condition builder tiers already use. Members join while they match and leave when they stop, with nobody assigning them by hand. This prototype runs entirely in your browser on sample data.

      1. The idea

      Manual today's segments

      Members are added and removed by hand: in the member form, with Assign members, or by an event rule's addToSegment / removeFromSegment effect. Nothing changes unless someone acts.

      Automatic new

      The segment stores conditions. A member is in it while the conditions hold and leaves when they stop. Membership is always the result of the rule, so the question "why is X in here?" is answered by the rule alone.

      How this relates to event rules: an event rule answers "when X happens, add them", which is one-off and never removes anyone. An automatic segment answers "who is X right now". Both stay, but event rules can only target manual segments, so the two never fight over the same membership.

      2. How it works

      Everything computed from a member's data is re-derived in one place, in dependency order:

      Member data changes→Automatic segments
      read: points, purchases, attributes, manual segments      →Tier
      read: … plus all segments      →Challenges
      handed to new joiners

      Segments run before tiers because tier conditions can already read segments. To rule out cycles, automatic segments cannot read the tier, and can only reference manual segments. So there are no chains between automatic segments and no ordering puzzles.

      3. The rule language

      This is the same RuleCondition (field · operator · value) that tiers and event rules use, with the same validator (validate_conditions) and the same evaluator (matches). It adds two small, flat extensions:

      • Match all / any: "match": "all" | "any". Tiers can express OR with two ranked tiers, but a segment has no such workaround. There is still no nesting.
      • notContains for segments ("don't include"), which lets "lapsed buyers, except Staff" be one rule.

      4. Guardrails

      1. No hand-editing automatic segments. POST /segments/{id}/assign answers 409 for an automatic segment. PATCH /members/{id} segmentIds manages manual segments only and rejects automatic ids with 400. The member form shows automatic segments as read-only chips.
      2. Event rules target manual segments only. addToSegment / removeFromSegment validation rejects automatic ones.
      3. At least one condition. An automatic segment with none would silently hold everyone.
      4. No cycles. Automatic conditions cannot use member.tier or other automatic segments. A manual segment used in an automatic segment's conditions can't be switched to automatic until that reference is gone.
      5. Switching modes is explicit. Manual → automatic replaces the hand-picked members with the rule's result, and the preview shows who leaves. Automatic → manual keeps the current members as they are.
      6. Leaving keeps challenges. A member who leaves keeps challenges they were already handed, just as removeFromSegment works today.
      7. Referenced segments can't be deleted. Deleting a segment used by a tier or automatic segment answers 409, naming what uses it. Today a tier can silently point at a deleted segment.

      5. Data model

      member_segments is unchanged: an automatic segment writes the same rows, so everything that reads membership (challenges, tiers, member counts, event-rule conditions) works untouched. Every existing segment becomes manual.

      9. Rollout

      1. phase 1 Automatic segments on today's fields: migration, refresh_member, guardrails, preview, console UI and MCP tools. Program-wide re-checks run in the request, as reapply_tiers does now.
      2. phase 2 Time-based fields and a nightly Vercel Cron. The card shows "checked 3 h ago". If a program outgrows in-request re-checks, program-wide refreshes move onto a queue.
      3. phase 3 Membership history: a member_segment_changes log (joined or left, why, when) on the member page and in the event log.

      Open decisions

      • Should automatic segments also allow hand-picked extras ("pinned" members)? Recommendation: not in v1. Membership that is always the rule's result stays explainable.
      • Should leaving a segment withdraw its unfinished challenges? Recommendation: no. That matches removeFromSegment today.
